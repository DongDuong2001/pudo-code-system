# PUDO Architecture

This document explains how the components of PUDO relate to each other, why the repository is structured the way it is, and how the execution flow works for each product surface.

---

## Overview

PUDO has three distinct product surfaces that work independently or together:

1. **Agent Config Layer** — Markdown files that configure how AI coding assistants behave in your repo
2. **CLI** — Executable workflow commands (`pudo check`, `pudo score`, `pudo doctor`)
3. **MCP Server** — A local stdio server that exposes PUDO operations as callable tools for compatible agents


## Component Breakdown

### 1. Agent Config Layer

The simplest surface. These are Markdown (or XML) files that coding agents read as context when you open a project.

| File | Tool | Purpose |
| --- | --- | --- |
| `AGENTS.md` | Codex, cross-tool | Shared PUDO workflow instructions |
| `CLAUDE.md` | Claude Code | Claude-specific memory bridge |
| `GEMINI.md` | Gemini | Gemini workspace instructions |
| `.cursor/rules/pudo-*.mdc` | Cursor | Modular Cursor rules per PUDO phase |
| `.github/copilot-instructions.md` | GitHub Copilot | Repo-wide Copilot instructions |
| `opencode/opencode.md` | OpenCode | OpenCode workspace instructions |
| `kiro/system-prompt.md` | Kiro | Kiro system prompt |
| `antigravity/instructions.xml` | Gemini/Antigravity | Antigravity XML format instructions |

These files are generated by `pudo init` and then live in the target repository. They require no runtime infrastructure — the AI tool reads them directly.

### 2. CLI

The CLI (`bin/pudo.js`) provides executable workflow commands that validate, score, and diagnose the operating layer.

```text
pudo-code-system
├── init          Generate agent rules, PR templates, quality checklists
├── check         Validate all installed PUDO config files
├── score         Score repository readiness (0–100)
│   ├── --json    Machine-readable JSON output (schema: schemas/pudo-score.schema.json)
│   └── --strict  Fail if score is below threshold
├── doctor        Diagnose workflow and policy gaps
└── lint          Lint prompt files for format compliance
```

**CLI execution flow:**

```text
User runs: npx pudo-code-system score

CLI (bin/pudo.js)
  └── Reads .pudo/config.json
        └── Evaluates criteria:
              - Instruction specificity
              - Context quality
              - Workflow evidence
              - AI/MCP safety config
              - Test presence
              - CI configuration
              - Benchmark evidence
              - Release traceability
        └── Outputs score + breakdown
              └── --json → follows schemas/pudo-score.schema.json
              └── --strict → exits non-zero if score < threshold
```

### 3. MCP Server

The MCP server (`packages/pudo-mcp-server/`) wraps CLI and config operations as callable tools that compatible agents can invoke directly via the Model Context Protocol.

**Security model:**

```text
MCP Server
  ├── Transport: stdio only (no network exposure in alpha)
  ├── Scope: one repository root (PUDO_PROJECT_ROOT env var)
  ├── File access: reads bounded to project root + PUDO package root
  ├── Write access: requires confirmWrite: true in every request
  ├── Shell execution: disabled
  └── Network access: disabled
```

**Tool implementation layout:**

```text
packages/pudo-mcp-server/
├── src/
│   └── server.ts           # MCP server entry, registers all tools
├── tools/
│   ├── core.ts             # Shared utilities (path resolution, config)
│   ├── pudo_init.ts        # initProject tool
│   ├── pudo_check.ts       # validateAgentRules tool
│   ├── pudo_score.ts       # scoreRepoReadiness tool
│   ├── pudo_quality_gate.ts # runQualityGate tool
│   ├── pudo_context_pack.ts # createContextPack tool
│   ├── pudo_doctor.ts      # doctor tool
│   └── pudo_session.ts     # updateSessionHandoff tool
└── tests/
    └── tools.test.ts       # Integration tests via MCP SDK client
```

## Data Flow: Session Handoff

One of PUDO's key features is session continuity. Here's how a typical multi-session workflow flows:

```text
Session 1
  Developer runs: pudo init
    → .pudo/config.json created
    → .pudo/session.md created (blank)
    → Agent rules generated

  Developer works (P → U → D → O)
    → Agent calls: pudo.updateSessionHandoff
        → Writes what was done, what's next, risks
        → Requires confirmWrite: true

Session 2
  Developer opens repo in AI tool
    → Agent reads .pudo/session.md automatically
    → Picks up exactly where Session 1 left off
    → No context reconstruction needed
```

## Repository Layout Rationale

| Directory | Rationale |
| --- | --- |
| `docs/` | All narrative documentation. Separated from methodology files so readers find it predictably. |
| `prompts/` | Organized by PUDO phase. Each phase is independently navigable. |
| `skills/` | Domain overlays for prompts. Separated from phase prompts to keep the library flat. |
| `quality/` | All quality enforcement. Checklists, gates, and anti-patterns together for easy cross-reference. |
| `examples/` | Numbered to imply progression. Each is self-contained. |
| `templates/` | Stack-specific scaffolds separate from methodology. Consumed by `pudo init`. |
| `benchmarks/` | Measurement infrastructure separate from methodology docs. Keeps the main docs clean. |
| `schemas/` | JSON schemas for machine-readable output. Separates spec from implementation. |
| `packages/pudo-mcp-server/` | Independent npm package. Separate lifecycle from the root package. |
| `bin/` | CLI entry point. Kept at root level so `npm run` and `npx` resolution works correctly. |
| `.pudo/` | Runtime state (config, session). Kept separate from docs and source. |
| `.github/` | Standard GitHub location for CI, templates, and Copilot config. |

## Technology Stack

| Component | Language | Key Dependencies |
| --- | --- | --- |
| CLI (`bin/pudo.js`) | JavaScript (Node.js) | None (zero runtime deps) |
| MCP Server | TypeScript | `@modelcontextprotocol/sdk@1.29.0`, `zod@3.25.0` |
| Schemas | JSON Schema (Draft 7) | None |
| CI | GitHub Actions | `ubuntu-latest`, `node 20` |

The CLI has zero runtime dependencies by design — `npx pudo-code-system` works in any Node.js 20+ environment without an install step.

## Security Boundaries

```text
┌──────────────────────────────────────────────────┐
│                  MCP Security Perimeter           │
│                                                  │
│  ┌──────────────────────────────────────────┐    │
│  │           Repository Boundary            │    │
│  │                                          │    │
│  │  ALLOWED reads:                          │    │
│  │  • Files under PUDO_PROJECT_ROOT         │    │
│  │  • Files under PUDO_PACKAGE_ROOT         │    │
│  │                                          │    │
│  │  BLOCKED:                                │    │
│  │  • Files outside project root           │    │
│  │  • .env, secrets, credentials           │    │
│  │  • node_modules/, .git/                 │    │
│  └──────────────────────────────────────────┘    │
│                                                  │
│  WRITES: require confirmWrite: true per call     │
│  SHELL:  disabled entirely                       │
│  NETWORK: disabled entirely                      │
│  TRANSPORT: stdio only (no HTTP/gRPC in alpha)   │
│                                                  │
└──────────────────────────────────────────────────┘
```
